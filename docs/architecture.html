Architecture

IRI strategy

Rationale

  • Hash IRIs are used because they reflect that terms cannot exist without an authoritative vocabulary in which they are described.[1] Furthermore they allow for a trivial — and frankly, desirable — implementation of dereferenceable IRIs, namely by resolving to the web documenation representation of the vocabulary.

  • Regarding the vocabulary and term names, although we do recognize the maintenance benefits of using opaque names, for the benefit of developers we have opted to go for meaningful names.

Each controlled vocabulary is identified by its IRI, and so are each of the terms contained in them:

This dynamicity infects the otherwise static version of the team’s data model, because a part of their model can now change outside of their control. The question is if this is really an issue. Let’s explore.

Terms are never removed, only added, so the only possible changes to the node shape that could occur is the addition of new terms. For things to break on the end of the data integration team, the following sequence of events then needs to occur:

  1. A new term must be added to the controlled vocabulary.

  2. One of the data producers adds data that uses this new term.

  3. Despite using an older version of the SHACL validation will succeed, despite using the integration team uses software to further ETL the data, and this software does not permit extraneous values and has not yet added the new term to the enumeration in the data model.

Only in this scenario will there be an error in the data integration pipeline. Note furthermore:

  • If a new term is added, typically users are informed about this.

  • Adding data which uses the new term does not come out of the blue. Again, communication, collaboration and planning goes into this, meaning all parties involved are likely in the know.

  • Even if an error occurs, adding the newly permitted term to the enumeration in the data model is trivial.

Interestingly, older and newer versions of the SHACL which import the node shape from the controlled vocabulary will behave equally, namely both import the up-to-date list of terms.

No release cycle or version number scheme will be used. Instead, in order to keep things simple, predictable and maintenable, controlled vocabularies will simply evolve [2]. New knowledge can always be added, including the introduction of new terms, but changes which alter the meaning or semantic scope of a term or the vocabulary are prohibited. In such cases a new term must be created with its own definition, and (if applicable) the old term can be deprecated. Terms and their definitions are never deleted. This way, any reference to a term or vocabulary will remain valid and accessible indefinitely (FAIR principles F1, A1 and A2).

Each modification to the vocabulary does result in a different version of it, but none of these representations are exposed through its identifying IRI and are merely accessible through the VCS. Effectively, this encodes having a single evolving identity whilst preserving historical lineage of the evolution.

Furthermore, it deserves mention that terms themselves do not have versions. Different versions of a vocabulary might provide different descriptions of terms contained in it, but there is no such thing as a "version of a term".

Evolution rules

The vocabulary evolves according to a set of rules which ensures the it remains semantically consistent and FAIR. Identities must remain stable, i.e. modifications must not lead to terms or vocabularies obtaining a meaning that is no longer compatible with earlier ones.
